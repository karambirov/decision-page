How to ship iOS versions
How I counted

Quarter: 13 weeks. A regular regression run takes a day and a half. For a release every two weeks I assumed 2 days: twice as many changes, but many flows are checked only once. This is an assumption; it needs checking with the testers.

Waiting: a fix is ready on a random day and on average waits half a release cycle.

Empty week: the branch has no change a person will see and no bug fix. The release lead decides on the day the branch is cut. If technical changes pile up for two weeks, the release goes out without skipping, so library updates don't fall behind.

A hotfix changes little code, so there is no point in testing the whole app for it. But fixes like these have broken neighboring flows before. A short manual check of the key paths catches such breakages and barely delays the release.

How to test a hotfix before release
Which fixes take the fast track if full regression testing is not needed
What the check covers and how to notice a miss

The short check list (test data): search, results, ticket details, card purchase, purchase with a promo code, sign-in, sign-out, account recovery, price alert subscription, price alert notification, profile, language change.

If the check misses something: we ship the urgent version as a phased release and watch the crash rate and successful purchases for the first day. If either gets worse, we pause the release and prepare the next fix. A version can't be rolled back in the App Store.

    What I didn't check

    • Every number on the page is made up: this is a test page. I didn't look at real release statistics.
    • I assumed regression testing for a two-week release takes 2 days. If it takes 3, releasing every two weeks saves nothing at all.
    • App Store review time for an urgent version: “about a day” comes from experience, not from a measurement.
    • How Android ships. If it has its own cadence, the shared release calendar may drift apart.
